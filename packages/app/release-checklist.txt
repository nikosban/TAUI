TAUI RELEASE CANDIDATE AND SABOTAGE CHECKLIST

PURPOSE

This is the canonical template for checks that automation cannot yet prove. Copy
the entire template into the Linear issue for every release candidate. Do not
edit this file to record a particular release.

A release candidate may be promoted only when:

- every applicable check has an owner, evidence, and a PASS result;
- every N/A result includes a reason;
- every FAIL result links a newly created or existing Linear issue; and
- the completed record is linked from the release candidate and release notes.

Use one of PASS, FAIL, or N/A for Result. Expected evidence describes what must
be captured; Evidence records the actual URL, attachment, CI run, screenshot,
video, log, package checksum, or concise observation.

REGRESSION-TEST SABOTAGE

Every bug-fix pull request must include the failing-test evidence requested by
.github/pull_request_template.md. Before applying the fix, or by temporarily
reverting/altering the fix locally, demonstrate that the regression test fails
for the intended reason. Record the exact command and a concise failure excerpt;
a screenshot or CI link may supplement, but not replace, the command. Restore
the fix and confirm the same test passes. Never commit the sabotaged code.

CANVAS ALTERNATIVE AND KNOWN LIMITATIONS

The canvas exposes document dimensions, active layer, active tool, and exact
selected-region coordinates and size to assistive technology. The Inspector also
exposes stable measurements and can copy them as JSON.

Direct cell painting, pointer-position inspection, marquee placement, and canvas
pan/zoom still require a visual pointer workflow. There is not yet a cell-by-cell
keyboard grid or fully navigable accessibility-tree representation of the
composed terminal image. Keep this limitation in release notes until a non-visual
canvas interaction model is implemented.
